# 推荐系统 v2 · 技术设计与任务拆解（SDD-Design & Tasks）

> 关联规格：[01-需求规格.md](./01-需求规格.md)。本文回答"怎么实现"，并给出任务清单与自测口径。

## 1. 总体架构

```
Request(limit, refresh)
   │
   ▼
RecommendationController ──► RecommendationServiceV2（引擎）
   │                              │
   │                              ├─ 0. 用户画像构建（有界查询）
   │                              │     favorites(≤50) + playCounts(GROUP BY, ≤200) + 偏好歌手/风格 Top-N
   │                              ├─ 1. 多路召回（每路独立 try-catch，全部有界查询）
   │                              │     CH-CF / CH-CONTENT / CH-ARTIST / CH-HOT / CH-FRESH
   │                              ├─ 2. 融合打分 + 硬过滤(FR-2) + 多样性打散(FR-3)
   │                              ├─ 3. 生成 reason/strategy（FR-4）
   │                              └─ 4. 用户级缓存（TTL 5min, refresh 绕过+采样, FR-5）
   ▼
List<RecommendItemVO>
```

## 2. 关键设计决策

| 决策点 | 选择 | 理由 | 备选（否决原因） |
|--------|------|------|------------------|
| 缓存介质 | 进程内 `ConcurrentHashMap` + TTL | 零依赖、demo 体量足够（NFR-1 明确不引 Redis） | Redis（超出 Out-of-Scope 边界） |
| 物品协同实现 | 种子歌曲 IN 查询共现用户 → 共现用户喜爱歌曲 IN 查询 | 两次有界查询替代两次全表扫描；种子 K=20、共现用户 ≤200、候选 ≤500 均有上界 | 预计算共现矩阵表（需离线任务，超范围） |
| 用户播放聚合 | JPQL `GROUP BY songId, COUNT` 新增仓储方法 | 替代"拉 200 条在内存里数"的旧实现 | — |
| 通道权重 | 代码常量类 `RecWeights` 集中定义 | NFR-3，一处可调 | 配置中心（超范围） |
| 多样性 | 结果内按主歌手贪心配额（ceil(0.4×N)） | 简单可测（AC 覆盖） | MMR（复杂度不成比例） |
| "换一批" | 绕过缓存 + Top-3N 池随机采样 | 无需服务端分页状态 | 游标分页（前端改动大） |
| personalized 响应演进 | 直接改 `RecommendItemVO`（前后端同仓同发布） | 本项目前端 dist 随仓库一起发布，不存在版本漂移窗口 | 双接口并存（冗余） |

## 3. 数据与查询设计（新增仓储方法）

```
FavoriteRepository
  + List<Favorite> findBySongIdIn(Collection<Long> songIds)            // CF 共现，songIds ≤ 20
  + List<Favorite> findByUserIdIn(List<Long> userIds, Pageable)       // 共现用户喜爱歌曲，userIds ≤ 200, limit ≤ 500

PlayHistoryRepository
  + @Query("SELECT ph.songId, COUNT(ph) FROM PlayHistory ph WHERE ph.userId=:uid GROUP BY ph.songId")
    List<Object[]> countPlaysGroupBySong(uid)                          // 用户播放聚合（替代内存计数）
  + @Query("SELECT DISTINCT ph.userId FROM PlayHistory ph WHERE ph.songId IN :songIds")
    List<Long> findUserIdsBySongIds(songIds)                           // 播过种子的用户，songIds ≤ 20

SongRepository
  + findByStatusAndGenreInOrderByPlayCountDesc(Integer, List<String>, Pageable)
  + findByStatusAndLanguageInOrderByPlayCountDesc(Integer, List<String>, Pageable)
  + @Query("SELECT DISTINCT s FROM Song s JOIN s.artists a WHERE a.id IN :artistIds AND s.status=1 ORDER BY s.playCount DESC")
    List<Song> findTopByArtistIds(artistIds, Pageable)
```

所有新查询满足 NFR-1（有界）；旧 `findAll()` 调用全部删除。

## 4. 打分与理由

- 种子权重：`w(song) = 2.0(若收藏) + ln(1 + 播放次数)`，时间衰减乘子见规格 FR-1。
- 通道内归一化：`score = w / maxW`（该通道候选中的最大权重），防止通道间量纲不可比。
- 融合后按 score 降序 → 硬过滤 → 多样性配额贪心 → 截取 limit。
- reason 模板（strategy 一并返回）：
  - cf：`听过《种子歌名》的人也在听`
  - content：`与你常听的「风格」相符` / `与你常听的语言相符`
  - artist：`你常听「歌手名」，试试 TA 的这首歌`
  - hot：`全网都在循环`
  - fresh：`30 天内的新鲜好歌`
- 冷启动（种子歌曲 < 3）：仅启用 HOT + FRESH 通道，理由照常返回。

## 5. 缓存失效钩子

- `RecommendationService.evictUserCache(Long userId)` 设为 public。
- `FavoriteService.toggleFavorite` 成功后调用；`PlayHistoryService` 新增记录后调用（注入方式，无循环依赖：二者均不反向依赖推荐服务）。

## 6. 前端改造（Discover.vue + api）

- 两个列表数据源由 `List<Song>` 变为 `List<RecommendItemVO>`：模板取 `item.song.*`，新增理由徽标（`el-tag`，按 strategy 着色：cf=紫 / content=蓝 / artist=绿 / hot=橙 / fresh=青）。
- `换一批` 请求追加 `refresh: true`。
- 收藏批量检查、播放队列均改用 `item.song.id`。
- 样式新增 `.reason-tag` 与卡片布局微调，不改动既有交互。

## 8. 风险与回退

- 风险1：JPQL 语法兼容性（先例：HQL 不支持 UPDATE+CASE）→ 新查询全部为 SELECT，启动期即校验，风险低。
- 风险2：CF 通道在小数据集上空结果 → 通道隔离 + HOT/FRESH 兜底，接口恒有结果（NFR-2）。
- 风险3：前端/后端响应结构同步发布 → 同仓库同提交，构建产物一起出（AC-7 回归兜底）。
- 回退方案：改动集中在 1 个服务 + 1 个控制器 + 1 个视图，git revert 单提交即可整体回退。
