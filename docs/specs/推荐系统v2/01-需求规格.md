# 推荐系统 v2 · 需求规格（SDD-Spec）

> Spec-Driven Development · 规格先行。本文档是推荐系统改造的唯一需求依据，实现与验收均以此为准。
> 状态：已评审通过（本仓库内评审） · 关联设计见 [02-技术设计与任务拆解.md](./02-技术设计与任务拆解.md)

## 1. 背景与问题

当前推荐实现（`RecommendationService`，基于协同过滤的初版）存在以下问题：

| # | 问题 | 证据 |
|---|------|------|
| P1 | **全表扫描**：每次推荐请求把收藏表、播放历史表整表加载进内存（`favoriteRepository.findAll()`、`playHistoryRepository.findAll()`），相似歌曲还对每个候选歌曲重复全表扫描 | `RecommendationService.getUsersWhoLikeSong / findSimilarUsers` |
| P2 | **算法单一**：仅共现计数，忽略内容特征（风格 genre / 语言 language / 歌手），无时间衰减，热门歌曲权重失衡 | 同上 |
| P3 | **无缓存**：每次进入发现页全部重算，同一用户连续请求重复付出 P1 的代价 | 无任何缓存层 |
| P4 | **不可解释**：推荐结果无理由，用户不知道"为什么推荐给我" | 接口只返回 `List<Song>` |
| P5 | **冷启动弱**：新用户只能拿到热门榜，无内容特征兜底 | `getHotSongs` 单一降级 |

## 2. 目标（Goal）

G1 性能可用：推荐链路杜绝全表扫描，接口响应在万级收藏 / 五万播放记录量级下保持亚秒级（验收口径见 §6）。
G2 算法升级：多路召回（协同 + 内容 + 歌手 + 热度 + 新鲜度）融合打分，支持时间衰减与多样性约束。
G3 可解释：每条推荐携带推荐理由与召回策略标识。
G4 冷启动：新用户（无收藏、播放 < 3 次）也能获得有意义的结果。
G5 前端呈现：发现页展示推荐理由，"换一批"按钮真正换掉结果。

## 3. 用户故事

- US-1 作为**登录用户**，进入"发现音乐"页，看到按我的口味排序的推荐歌曲，每首标注推荐理由。
- US-2 作为**听过一些歌的用户**，希望和我听过相同歌的人喜欢的歌出现在推荐里，理由注明"基于哪首歌"。
- US-3 作为**新注册用户**，进入发现页能看到热门与新歌，而不是空列表。
- US-4 作为任意用户，点击"换一批"后得到与上一批不同的结果。
- US-5 作为**已收藏/反复听过**某歌的用户，不再被重复推荐这首歌。

## 4. 功能需求（FR）

### FR-1 多路召回与融合排序
| 编号 | 召回通道 | 数据来源 | 说明 |
|------|----------|----------|------|
| CH-CF | 物品协同 | 收藏 + 播放共现 | 用户 Top-K 种子歌曲（收藏权重 2.0 + log(播放次数)），找同样听过/收藏这些歌曲的用户，取其喜爱歌曲聚合 |
| CH-CONTENT | 内容特征 | genre / language | 与用户偏好风格、语言相符的歌曲，按播放量排序 |
| CH-ARTIST | 歌手维度 | song_artist 关联 | 用户偏好歌手的其它歌曲 |
| CH-HOT | 全局热度 | play_count 榜 | 兜底与多样性来源 |
| CH-FRESH | 新鲜度 | 近 30 天创建歌曲 | 新歌曝光 |

融合：`score = Σ (通道内归一化分 × 通道权重)`，权重 CF=0.50 / CONTENT=0.25 / ARTIST=0.15 / HOT=0.07 / FRESH=0.03（常量可调）。
播放历史时间衰减：最近 7 天权重 ×1.0，30 天 ×0.6，90 天以上 ×0.3（阈值常量）。

### FR-2 过滤规则（硬性）
- 只推荐 `status = 1`（上架）歌曲。
- 排除用户已收藏的歌曲。
- 排除用户播放次数 ≥ 3 的歌曲（听腻规则）。

### FR-3 多样性
- 最终结果中同一主歌手的歌曲不超过 40%（向上取整），贪心打散。

### FR-4 推荐理由
每条结果携带 `reason`（中文文案）与 `strategy`（召回通道标识：`cf` / `content` / `artist` / `hot` / `fresh`）。理由必须来自真实依据（如共现种子歌曲名、风格名、歌手名），禁止编造。

### FR-5 缓存与"换一批"
- 按用户维度缓存推荐结果，TTL 5 分钟；用户新增/删除收藏、记录播放时主动失效该用户缓存。
- 接口支持 `refresh=true`：绕过缓存并从扩大 3 倍的候选池中随机采样返回，保证"换一批"体感不同。

### FR-6 接口契约（本次演进）

| 接口 | 变更 | 响应 |
|------|------|------|
| `GET /music/recommend/personalized` | 响应结构演进（**破坏性**，前后端同版本发布） | `List<RecommendItemVO>` |
| `GET /music/recommend/guess-you-like` | 同上 | `List<RecommendItemVO>` |
| `GET /music/recommend/similar-songs/{songId}` | 结构不变，内部引擎升级 | `List<Song>`（保持兼容） |
| `GET /music/recommend/playlists` | 不变 | `List<Playlist>`（保持兼容） |

```json
// RecommendItemVO
{
  "song":     { ...Song 全量字段 },
  "score":    12.83,
  "reason":   "听过《素颜》的人也在听",
  "strategy": "cf"
}
```

## 5. 非功能需求（NFR）

- NFR-1 **查询有界性**：推荐链路所有数据库查询必须有 LIMIT / Pageable / IN 上界约束，代码评审以"无无界查询"为通过标准。
- NFR-2 **降级安全**：任何召回通道异常不导致接口失败（try-catch 隔离，空通道跳过）。
- NFR-3 **可配置**：通道权重、种子数 K、多样性上限、缓存 TTL 以常量集中定义，一处可调。
- NFR-4 **兼容运行时**：Spring Boot 2.4 / Java 8 / Hibernate 5.4 约束内实现（注意：HQL UPDATE 不支持 CASE WHEN 等既有限制）。

## 6. 验收标准（Acceptance Criteria）

| # | 断言 | 验证方式 |
|---|------|----------|
| AC-1 | `personalized` / `guess-you-like` 返回 `List<RecommendItemVO>`，每项 `song`/`score`/`reason`/`strategy` 齐全且 reason 非空 | E2E |
| AC-2 | 结果不含已收藏歌曲、不含 `status != 1` 歌曲 | E2E |
| AC-3 | 结果不重复（按歌曲去重），数量 = min(limit, 可用候选数) | E2E |
| AC-4 | 新注册用户（零行为）请求推荐返回热门/新歌，reason 分别为热门/新歌类文案 | E2E |
| AC-5 | 有收藏+播放行为的用户，结果中出现 `cf`/`content`/`artist` 策略的条目 | E2E（种子数据） |
| AC-6 | `refresh=true` 返回的列表与不带 refresh 的列表不同（在候选充足前提下） | E2E |
| AC-7 | 相似歌曲接口仍返回 `List<Song>`，全流程不回归 | E2E 回归 |
| AC-8 | 推荐链路无 `findAll()` 全表调用 | 代码审查 |
| AC-9 | 单次推荐请求（本地隔离环境）耗时 < 3s（E2E 冒烟阈值；生产目标 P95 < 500ms 挂运维观测） | E2E 计时 |
| AC-10 | 历史全部 111 项 E2E 断言不回归 | E2E 回归 |

## 7. 明确不做（Out of Scope）

- 不引入外部中间件（Redis / ES / ML 平台），缓存用进程内实现。
- 不做离线批训练、向量化模型（数据量未到阈值，保持在线轻量计算）。
- 不改歌单推荐（`/playlists`）算法，仅保留既有实现。
- 不做 A/B 框架与曝光埋点（留待 v3）。
