### 功能与数据一致性类
- **好友互发请求后接受必然 500**（反向记录撞唯一约束）→ 接受时存在则更新状态（`FriendshipService`）。
- **点赞/评论数/播放数用"读-改-写"并发丢失** → 全部改为原子 `UPDATE`（`SongRepository.incrementPlayCount`、`UserMomentRepository`、`SongCommentRepository`）。注意：Hibernate 5.4 的 HQL **不支持 UPDATE 里写 CASE WHEN**，递减一律用 `WHERE count > 0` 模式（启动即校验，编译期发现不了）。
- **删除评论遗留孤儿数据**（回复的点赞、回复的回复）→ 递归收集全层级级联删除；**删除动态全表扫描找点赞** → 改 `deleteByMomentId`。
- **歌曲分享点赞可无限刷** → 新增去重表 `tb_song_share_like`（`entity/SongShareLike.java` + `SongShareLikeRepository`，由 `ddl-auto=update` 自动建表，部署后数据库会多出这张表）。

- **`docker-compose.yml` 挂载不存在的 `database.sql`** → 指向 `src/main/resources/db/init.sql`。
- **OSSUtil 启动日志打印 accessKeyId** → 删除；上传扩展名解析对无扩展名文件不再越界。

## 4. 交付三：推荐系统 v2（SDD）

规格：`docs/specs/推荐系统v2/01-需求规格.md`（问题清单、FR/NFR、AC-1~10）· `02-技术设计与任务拆解.md`（架构、决策表、任务、跟踪矩阵）。

**架构**：五路召回融合打分——CF 物品协同(0.50) / 内容特征 genre+language(0.25) / 歌手维度(0.15) / 全局热度(0.07) / 新鲜度(0.03)；"猜你喜欢"用另一组大盘权重。种子权重 = 收藏 2.0 + ln(1+播放) × 时间衰减（7 天 1.0 / 30 天 0.6 / 90 天 0.3）。硬过滤（已收藏/播放≥3 次/下架）→ 主歌手 40% 配额打散 → 每条结果带 `reason`（如"听过《素颜》的人也在听"）与 `strategy` 标识。用户级缓存 TTL 5 分钟，收藏/播放变更主动失效，`refresh=true` 从 3 倍候选池随机采样（换一批）。

**硬性成果**：推荐链路杜绝全表扫描（旧实现每次请求 `findAll()` 整表加载收藏+播放历史）；接口本地实测 ~180ms；冷启动用户自动落到热门+新歌。

**契约变更（破坏性，前后端同版本发布）**：`/music/recommend/personalized` 与 `/guess-you-like` 响应由 `List<Song>` 变为 `List<RecommendItemVO>`（`{song, score, reason, strategy}`）；`/similar-songs/{id}` 与 `/playlists` 契约不变。

**文件**：重写 `service/RecommendationService.java`；`RecommendationController.java`；新增 `dto/RecommendItemVO.java`；`FavoriteRepository`/`PlayHistoryRepository`/`SongRepository` 各增有界查询；`FavoriteService`/`PlayHistoryService` 挂缓存失效钩子；前端 `Discover.vue` 理由徽标（按策略着色）+ 换一批。

## 11. 2026-09-05 追加：管理后台封面排查 + SW 外域放行 + 导入链路验证

**现象**：管理后台改版后，用户浏览器（127.0.0.1:4173/#/admin）歌手头像显示字母、歌曲封面显示耳机占位。

**排查结论（证据链）**：
1. 数据层正常：直连库与 `/api/admin/song|artist/list` 均返回完整 cover/avatar URL（184 首歌 OSS 封面、40 位歌手外站头像）。
2. 渲染层无 bug：在受控 Chromium 中以相同 dist + 相同代理访问 #/admin，**10/10 封面与 10/11 头像全部解码成功**（img.naturalWidth > 0，el-image 无 error 槽；唯一字母头像对应 avatar 为 NULL 的测试数据，属正常降级）。
3. 唯一的页面级差异机制是 Service Worker：旧版 sw.js 对**所有**非导航 GET（含跨域图片）`respondWith`，SW 内 fetch 一旦失败会被兜底替换成 offline.html → 图片必然解码失败。而直接在浏览器地址栏打开图片 URL 不经过 SW，能正常显示——与"图片源没问题、页面里不显示"的现象吻合。
4. 修复：`public/sw.js` 新增**跨域请求直接放行**（`url.origin !== self.location.origin` 即 return，跨域响应本就进不了同源 Cache，拦截只有风险没有收益），缓存版本升至 `sheep-music-v4`（activate 自动清 v3 旧缓存）。
5. 用户浏览器若刷新后仍不显示：按 Ctrl+Shift+R 强刷让新 SW 接管；再不行检查系统代理/VPN（如"自由猫"）对 baidu/aliyuncs/y.qq.com 的拦截与浏览器扩展的图片过滤。

**导入中心验证（e2e 隔离库实例，PORT=19001）**：
- 现有实现已符合"直接上传音频 → OSS 返回 URL"：`el-upload → /api/upload/music` 返回 `data.url` 回填表单，再 POST `/admin/song/import`（后端 SongController/ArtistController 已有 `/import` 端点，DTO 与前端封装字段一一匹配）。
- 实测通过：歌手批量导入去重（3 名 → 2 建 1 跳过）；`song/import` 创建成功（已有歌手 + 按名自动建新歌手、字段落库、空参 400 校验）。
- **⚠ 阻塞项：本机环境变量里的 OSS AccessKey（LTAI5tFpjg…）已被阿里云判定不存在（InvalidAccessKeyId），当前所有上传必然 500。** 需到阿里云控制台更换有效的 `ALIYUN_OSS_ACCESS_KEY_ID/SECRET`。
- 顺带修复：ContentImport.vue 两个 el-upload 此前未绑 `:on-error`、成功回调忽略非 200——现在上传失败（含 HTTP 500 与业务 code≠200）都会弹出后端错误信息，不再静默。

- **防幻觉核心**：工具条目带 ref 下标，模型只能以 refs 提名，song_card 字段全部由编排器从工具数据回填（LLM 永不生成 URL/ID）
- `POST /agent/dj/stream` SSE 事件协议：stage/thought/action/observation/text_delta/song_card/error/done；无密钥 error 降级
- 前端：Layout 悬浮 DJ 按钮（荧光绿渐变 FAB）+ `DjDrawer.vue` 对话抽屉（阶段可视化/卡片网格/播放整组/全部入队）；`api/agent.js` 用 fetch+ReadableStream 解析 SSE（EventSource 带不了 JWT）
- SecurityConfig 补 `DispatcherType.ASYNC` permitAll（SseEmitter 完成后的异步回派此前被 Security 6 拦截）

**两个关键坑（智谱 × Spring AI）**：
1. **路径双前缀 404**：Spring AI 默认拼 `/v1/chat/completions`，智谱 base-url 已含 `/v4` → 404 `/v4/v1/chat/completions`。修复：`spring.ai.openai.chat.completions-path: /chat/completions`
2. glm-4.5-air 是推理模型：先输出思考内容（耗 token），JSON 结构化质量高但响应慢（整轮 15~40s）——提示词要求"只输出一个 JSON"+ 防御性提取（剥围栏+平衡括号扫描）+ 失败重试一次 + 逐步降级

**验证**：curl SSE 冒烟完整事件序列（"下雨天"→ 4 步 ReAct + 97 个 text_delta + 8 张混排卡片 + Critic 74 分通过）；真机 Edge 全流程（抽屉提问 → 卡片 → 点播《晴天》正常播放）；**E2E 五套全绿：agent-test 13（真实 LLM 联测，断言聚焦协议与非确定性容忍）/ api 111 / rec 20 / external 20 / ws 7**。

**运行配置**：`AGENT_API_KEY`（用户提供，**不入仓库**；联测完建议轮换）+ `AGENT_MODEL=glm-4.5-air`（资源包 12M tokens，2026-11-28 到期）。智谱 search-std 资源包（100 次）留作 P2"联网音乐资讯"工具。

**P2 展望**：会话记忆/口味画像/显式反馈、CLAP 语义检索（Python 离线编码）、逐首 reason 细化。

## 23. 小屋 DJ Agent 工作流总结（agent-v1 P1 运行手册）

> 代码位置：`back/.../agent/`（AgentPrompts / DjTools / AgentOrchestrator / AgentController）
> 前端：`layouts/Layout.vue`（入口）· `components/DjDrawer.vue`（抽屉）· `api/agent.js`（SSE 读器）
> 规格：`docs/specs/agent-v1/`

### 23.1 全链路一图流

```
用户在 DJ 抽屉输入（"来点适合下雨天听的歌"）
  │ POST /agent/dj/stream {query}（JWT 鉴权，SseEmitter 0L 超时）
  ▼
AgentController ── 线程池(4) ──▶ AgentOrchestrator.run()
  │
  ① Dispatcher   1 次 LLM call（temp 0.3 / 1024 tok）
  │    输出意图 JSON：{scene, mood, genres[], artists[], language, count, scope: local|web|mixed, intentSummary}
  ▼
  ② Librarian    ReAct 循环，≤4 步（temp 0.4 / 1600 tok），每步推 thought/action/observation 事件
  │    模型输出 {thought, action, args}，编排器执行动作并把结果以 "[ref=N] 标题 - 歌手（来源）" 回填
  │    动作：search_local（SongService 检索）
  │         search_web（ExternalMusicService→歌曲海：搜索/封面/歌词同源）
  │         recommend（RecommendationService v2 个性化，带 reason）
  │         finish(refs[])  —— 只能用已收集条目的 ref 编号提名（防幻觉核心）
  ▼
  ③ DJ           stream() 流式串场词（temp 0.85 / 1200 tok）→ 逐段 text_delta 事件
  ▼
  ④ Critic       打分 {score, pass, feedback}（temp 0.2 / 800 tok）
  │    pass=false 且轮次<2 → feedback 注入 Librarian 历史回炉重检索
  ▼
  song_card × N（≤10，本地/歌曲海混排）→ done
```

**真实运行样例**（"来点适合下雨天听的歌"，glm-4.5-air）：
`search_local("雨天")` 无结果 → `search_web("雨天")` 得 6 条 → `recommend(limit=2)` 得本地 2 首 → `finish(refs)` 提名 8 首（6 歌曲海 + 2 本地）→ Critic 74 分通过 → 97 个 text_delta + 8 张卡片。

### 23.2 四角色职责速查

| 角色 | 提示词常量 | 职责 | 输出契约 |
|------|-----------|------|----------|
| Dispatcher | `AgentPrompts.DISPATCHER` | 意图拆解：场景/情绪/风格/歌手/语言/数量/检索范围 | JSON `{...intentSummary}` |
| Librarian | `AgentPrompts.LIBRARIAN` | ReAct 工具循环收集候选 | JSON `{thought, action, args}` / finish 时 `{..., refs[]}` |
| DJ | `AgentPrompts.DJ` | 表达层：80~140 字口语化串场词，带 2~3 个歌名 | 纯文本（流式） |
| Critic | `AgentPrompts.CRITIC` | Reflection 质检：匹配 70% + 多样性 15% + 数量 15% | JSON `{score, pass, feedback}` |

### 23.3 工具集（DjTools.java，均为既有 Service 的薄包装）

| 动作 | 数据源 | 返回条目字段 |
|------|--------|--------------|
| search_local | `SongService.searchSongs`（status=1 过滤） | type=local, songId, title, artist, cover, genre, language, url |
| search_web | `ExternalMusicService.search("gequhai")`（曲库供应链 v1.2） | type=gequhai, sourceTrackId, title, artist, cover, streamUrl, isExternal |
| recommend | `RecommendationService.getPersonalizedSongs`（五路召回） | 同 local + reason（如"听过《素颜》的人也在听"） |

### 23.4 防幻觉机制（本设计的核心）

1. 工具条目进入**候选索引**（去重键 type+title+artist，索引上限 40）时分配递增 `ref`；
2. LLM 的观察里只看到 `[ref=N] 标题 - 歌手（来源）`，finish 只能提交 ref 数组；
3. song_card 的全部字段（songId/streamUrl/封面）由编排器按 ref 从索引**回填**——LLM 永远不生成 URL/ID；
4. E2E（agent-test.mjs）断言卡片字段形态：本地必有 songId、歌曲海必匹配 `stream?source=gequhai&trackId=\d+`。

### 23.5 SSE 事件协议（前端 DjDrawer.vue 的消费方式）

| event | data | 前端行为 |
|-------|------|----------|
| stage | {stage, status, round?, intent?/score?} | 状态行文案（理解需求/翻找曲库/质检/组织语言） |
| thought / action / observation | {step, round, …} | Librarian 过程可视化（action 映射成"歌曲海"雨天"…"） |
| text_delta | {delta} | 追加到消息正文（流式打字感） |
| song_card | {source, songId?/sourceTrackId+streamUrl, title, artist, cover, reason?} | 渲染卡片（外源卡异步回填封面） |
| error | {message} | 红字提示（无密钥降级也走这里） |
| done | {count, intro} | 解除输入禁用，显示"播放整组/全部入队" |

### 23.6 降级与容错（每层都有退路）

| 故障 | 行为 |
|------|------|
| 未配 AGENT_API_KEY | Controller 直接 error 事件："请配置 AGENT_API_KEY…"，不触发 LLM |
| LLM 输出解析失败 | 剥围栏 + 平衡括号提取；重试一次；Librarian 仍失败→跳过该步；Critic 失败→视为通过 |
| Librarian 4 步耗尽未 finish | 取已收集条目前 10 兜底 |
| 工具异常（如歌曲海波动） | observation 告知模型，其自适应换词/换工具；recommend 内部吞异常返回空 |
| Critic 两轮都不达标 | 用最后一轮候选输出，不阻塞 |
| 客户端断开 | send 抛异常 → 中止编排，静默 complete |

### 23.7 配置与成本

- `AGENT_API_KEY`（智谱，环境变量，不入仓库——**当前密钥已在聊天记录暴露，建议轮换**）
- `AGENT_MODEL=glm-4.5-air`（资源包 12M tokens，至 2026-11-28；推理模型：先思考后输出，JSON 稳但整轮 15~40s）
- `spring.ai.openai.chat.completions-path: /chat/completions`（智谱路径适配，勿删——默认 /v1 会 404）
- Security：/agent/** 需登录；`DispatcherType.ASYNC` permitAll 为 SSE 必需（勿删）
- 智谱资源包还有 search-std ×100 次（联网搜索工具），留作 P2

### 23.8 已知边界与 P2 方向

1. 无多轮记忆：每次请求独立（追问"换成周杰伦的"= 重新描述需求）；P2 接会话窗口 + 口味画像
2. 逐首 reason 未做（串场词承载）；P2 细化
3. CLAP 语义检索未接（P2：Python 离线编码 184 首 → 内存向量索引）
4. 歌曲海源的稳定性直接放大到 search_web 工具（改版需跟 GequhaiProvider）
5. Curator（P3）定位已调整为用户上传/AI 生成入库审核；虚拟艺人厂牌（P4）需 GPU

## 24. 2026-09-06 追加：agent-v1 P2——会话记忆 / 口味画像 / 逐首 reason / 显式反馈

**新增能力**（规格见 docs/specs/agent-v1/ §8）：
1. **会话记忆**：请求带 `sessionId`（前端抽屉生命周期内复用，服务端首事件 `session` 归一化回传）；`DjSessionStore` 内存会话库（TTL 30min / 200 会话 / 每会话近 10 轮对话 + 上轮已推荐清单）。对话历史（近 6 轮）与"避免重复上轮"约束注入 Dispatcher/Librarian/DJ 三角色提示词。实测第二轮"换成周杰伦的，多来几首"命中周杰伦歌曲。
2. **口味画像**：`DjTools.tasteProfile(userId)`——播放历史近 50 条（`findByUserIdWithSongDetails` JOIN FETCH）聚合常听歌手 Top5 / 风格 Top5 / 最近播放 5 首，注入三角色提示词。确定性数据、零 LLM 成本。"随便来点歌"类需求由此个性化。
3. **逐首 reason**：DJ 从 stream() 改为单次 call() 输出 JSON `{intro, reasons[]}`（reasons 与候选顺序对齐），intro 切片伪流式发出（推理模型 stream 同样要等思考完成，体验无差、少一次调用）；song_card 携带 reason，前端卡片显示荧光绿小标签。实测覆盖 8/8。
4. **显式反馈**：卡片组完成后的"多来点这样的 / 换个口味"快捷按钮——本质是携带会话记忆的预置 query，由 Dispatcher 结合历史理解意图。

**验证**：agent-test 扩至 **18 项全绿**（+session 事件 / 会话连续性第二轮命中周杰伦 / 同 sessionId 回传 / reason 覆盖 8/8）；四套回归全绿（api 111 / rec 20 / external 20 / ws 7）；真机 Edge 多轮实测通过。

**运维注意**：
- 推理模型延迟波动大（Dispatcher 单步 10~60s，整轮最差 ~2 分钟）——阶段可视化对冲；追求响应速度可把 `AGENT_MODEL` 换 glm-4.5-flash（非推理、免费，质量略降）
- 会话记忆在内存（重启丢失）；持久化到 MySQL 属 P3
- `DjSessionStore` 若多实例部署需换集中式存储（当前单实例定位无此需求）
